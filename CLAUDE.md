# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Structure

Multi-loader Kotlin Minecraft mod (MC 1.21.x, Java 21+, Kotlin 2.x). Two namespaces, each split into `common`/`fabric`/`neoforge`:

- `to_base/` -- "To Lay the Foundations" base mod (library mod providing shared hooks, event system, registry registration, data-driven wiki, Kotlin helpers)
- `to_sky_and_stars/` -- "To Sky and Stars" content mod (space race era nuclear theme; depends on `:to_base:common`)

Each namespace has a `properties.toml` (`group`, `version`, `modId`, `modName`, optional `description`). The root `build.gradle.kts` parses these to set `group`, `version`, and project extras. Versions catalog is `libs.versions.toml`.

Subprojects follow `<namespace>/<loader>` convention: `to_base/common`, `to_base/fabric`, `to_base/neoforge`, `to_sky_and_stars/common`, etc.

## Build & Run Commands

**Build everything (all mods, all loaders):**
```
./gradlew build
```

**Single mod + single loader:**
```
./gradlew :to_base:neoforge:build
./gradlew :to_sky_and_stars:fabric:build
```

**Tagged builds (equivalent of CI tagged release):**
```
./gradlew :to_sky_and_stars:common:build :to_sky_and_stars:fabric:build :to_sky_and_stars:neoforge:build
./gradlew :to_sky_and_stars:neoforge:runData && git diff --exit-code
```

**Run data generators (neoforge):**
```
./gradlew :<mod>:neoforge:runData
```
Providers write into `<mod>/neoforge/src/main/generated` (set by `--output` in `neoforge/build.gradle.kts`), which is **gitignored**; `ToForgeDataMod` then copies everything back into `<mod>/common/src/main/resources`, which is the tracked copy the mod actually ships. So `git diff --exit-code` afterward — always run it — is checking the common resources, not the generator's own output directory. `ToForgeDataMod.resources` derives that destination by string-replacing `neoforge`→`common` and `generated`→`resources` in the pack output path, and `deleteExisting` clears the replaceable files there first so a rename leaves nothing behind.

**Run the game:** Use IDE run configs generated by Loom/ModDev (`client`, `server`, `data`, `test`). Run configs for Neoforge are registered in `neoforge/build.gradle.kts` and appear after Gradle sync.

**Run unit tests (plain JVM, no game or modloader):**
```
./gradlew test
./gradlew :to_base:common:test
```

**Run game tests (in a live level, Neoforge only):**
```
./gradlew runTest
./gradlew :<mod>:neoforge:runTest
```

## Gotchas

- **Checkstyle covers Java, Detekt covers Kotlin.** `config/checkstyle/checkstyle.xml` enforces the conventions the existing mixins already follow: 4-space indentation (no tabs), blank-line padding inside type bodies, IntelliJ import order, whitespace/brace/naming rules, and compact annotations (`@At("TAIL")`, not `@At(value = "TAIL")`). Mixin method names may carry a `<modid>$` prefix. Javadoc is required on every type, method, field and enum constant regardless of visibility, with a `@param` for each parameter (including type parameters) and a `@return` on non-void methods; `@Override` methods are exempt. `@see` and `{@link}` targets must be fully qualified. An end-of-line comment is written `//like this`, with no space after the slashes — `LineCommentSpacing` is a `MatchXpath` on the comment node rather than a regex, because a regex cannot tell a comment from `"http://…"` in a string literal. Javadoc and block comments are unaffected and keep the space after the asterisk (`JavadocMissingWhitespaceAfterAsterisk`). Line length and magic numbers are deliberately not checked — the config header explains why. Wired up in `multiloader-common.gradle`, so `checkstyleMain` runs as part of `check`/`build` (including in CI). Run it alone with `./gradlew checkstyleMain`.
- **Kotlin linting is Detekt**, configured in `config/detekt/detekt.yml` and wired up in `multiloader-common.gradle`, so `detekt` runs as part of `check`/`build`. Run it alone with `./gradlew detekt`. The config is a *delta* over Detekt's defaults (`buildUponDefaultConfig = true`), so any rule not named in the file keeps its default state; `./gradlew detektGenerateConfig` writes out the full default set for reference (it refuses to overwrite an existing file). Detekt validates the config and fails on an unknown rule or property name, and property names differ from Detekt 1.x — `threshold` is now `allowedLines`/`allowedComplexity`/`allowedFunctionParameters` and so on. The `ktlint` rule set is ktlint wrapped as Detekt rules; the root `.editorconfig` mirrors it for the IDE but **is not read by Detekt**, so any change has to be made in both places. Like line length and magic numbers, the wrapping rules that fight the codebase's compact lambda/argument style are deliberately off, with the reasons written into the file. Each project's `detekt` task only scans its own `src/*/{java,kotlin}` directories, so the common sources the loader projects pull into `compileKotlin` are checked once, by the project that owns them — the same property `checkstyleMain` has.
- **Custom Detekt rules live in `:meta`.** It is a real subproject (not part of `buildSrc`) because Detekt needs the rules on the *analysis* classpath at execution time, not the buildscript classpath; `multiloader-common.gradle` adds it via `detektPlugins project(':meta')`. It compiles against `dev.detekt:detekt-api` as `compileOnly` and is discovered through `META-INF/services/dev.detekt.api.RuleSetProvider`. The rule set id is `to-style`, which is also its section name in `detekt.yml`. Adding a rule means adding it to `ToStyleRuleSetProvider` *and* to the `to-style` section of `detekt.yml` — custom rules are inactive unless the config turns them on. It holds:
  - `TypeOpenBraceBlankLine` / `TypeCloseBraceBlankLine` — Kotlin counterparts of the same-named Checkstyle rules, requiring the blank-line padding inside type bodies that ktlint's `NoEmptyFirstLineInClassBody` and `NoBlankLineBeforeRbrace` forbid, which is why those two are disabled. The convention does **not** extend to companion objects, enum classes (including enum entry bodies) or anonymous `object` expressions; each is a config flag on both rules. Single-line and empty bodies are skipped, matching the Java regexes.
  - `LineCommentSpacing` — an end-of-line comment's text starts immediately after its slashes (`//like this`), which is the reverse of ktlint's `CommentSpacing`, so that rule is off. It carries over the half of `CommentSpacing` that still applies, `requireSpaceBeforeComment`, so a comment trailing code is still separated from it. Only `EOL_COMMENT` is visited — block and KDoc comments keep the space after the asterisk. The leading slash run may be longer than two (a `////` divider) and the text must start after all of it; an empty `//` is left alone. `.editorconfig` sets `ij_kotlin_line_comment_add_space = false` so the IDE's comment action agrees.
  - `PropertyNaming` — camelCase on every property (class member, object member, top level, local), which is why all three of `naming>VariableNaming`, `naming>ObjectPropertyNaming` and `naming>TopLevelPropertyNaming` are off. Their defaults allow underscores anywhere, and once tightened none of them can spare the library types, whose properties deliberately mirror the snake_case resource name they register — `VariableNaming` has an `excludeClassPattern` but never sees an object's properties, and `ObjectPropertyNaming`, which does, has no equivalent. `excludeTypePattern` (`.*Library.*`) is matched against the type's own name *and* each supertype name. `constantPattern` additionally accepts `SCREAMING_SNAKE_CASE`, but only for a `const val` — Kotlin's own definition of a constant. A top-level or object `val` that could not carry the keyword because it holds an object rather than a compile-time value (`val CODEC = simpleCodec(...)`) is an ordinary property and must be camelCase; `treatObjectValsAsConstants` restores the looser reading and is off.
  - `UndocumentedType` / `UndocumentedFunction` / `UndocumentedProperty` — KDoc on every type, function, property and enum constant at *every* visibility, matching the Javadoc block in `checkstyle.xml`. The built-in `comments>UndocumentedPublic*` rules only reach the public and protected surface, so they are off rather than supplementary. Overrides are exempt, as `@Override` methods are on the Java side.
  - `MissingKDocTags` — `@param` for every value and type parameter, `@return` where there is a value to return. Only declarations that *already* carry KDoc are checked, so a wholly undocumented one is reported once by the rules above instead of once per tag. `comments>OutdatedDocumentation` is on alongside it and covers the opposite direction (a `@param` for a parameter that no longer exists, wrong order); it stays silent when there are no tags at all, which is why both are needed. Detekt runs without type resolution here, so an expression-bodied function with no declared return type is assumed to return a value unless its body is literally `Unit` — the `checkInferredReturn` flag.
  - `MissingSinceTag` — a `@since` naming the version a declaration first appeared in, on every documented type, function, secondary constructor, property and enum constant. It is the only rule in the config scoped by path: `includes: ['**/to_base/**']` limits it to the library mod, whose declarations are the published API, and every other namespace is never visited. Detekt's `includes`/`excludes` are `java.nio` globs matched against the whole file path, so the leading `**/` is required — a bare `to_base/**` matches nothing. Like `MissingKDocTags` it only checks declarations that *already* carry KDoc, so an undocumented one is still reported once, by the `Undocumented*` rules. `versionPattern` (default `\d+\.\d+\.\d+`) is matched against the whole tag text, so it also catches an `@since` with nothing after it; set it to `.*` to check only that the tag is present.
- **Detekt is pinned to a 2.0 alpha** (`dev.detekt`, not the old `io.gitlab.arturbosch.detekt`) because 1.23.8 cannot run on a JDK 25 daemon at all — its bundled IntelliJ `JavaVersion.parse` throws on `25.0.3`. Two knock-on details: reports are `html`/`checkstyle`/`sarif`/`markdown` (no `xml`/`txt`), and `build.maxIssues` in the config file is gone, replaced by `failOnSeverity` on the Gradle extension.
- **`.java` and `.kt` files must stay in their own source directory.** `checkSourceLayout` (defined in `multiloader-common.gradle`, hangs off `check`) fails the build on a `.kt` file under `src/*/java` or a `.java` file under `src/*/kotlin`. Neither mistake fails a compile on its own — `compileJava` only globs `**/*.java` so stray Kotlin is silently dropped, and `compileKotlin` parses `.java` for resolution without emitting class files for it, so stray Java compiles and then goes missing at runtime. The `common` projects also publish the two directories as separate `commonJava`/`commonKotlin` artifacts that the loader projects compile individually. Run it alone with `./gradlew checkSourceLayout`.
- **Two kinds of test, and they reach different code.** Unit tests are plain JUnit 6 + MockK under `src/test/kotlin` in the `common` projects, run by `./gradlew test` as part of `check`/`build`. They have no modloader, level or save — `to_base/common/src/test/kotlin/net/jidb/to/base/test/MinecraftBootstrap.kt` starts just enough of the game (once per test JVM) for `BuiltInRegistries` and real `BlockState`s to be readable, which is also why anything mockk subclasses needs it to have run first; `TestEnvironmentService`/`TestRegisterService` stand in for the loader services via `META-INF/services` under `src/test/resources`. `to_base/common/build.gradle.kts` calls `addModdingDependenciesTo(sourceSets.test.get())` to put the deobfuscated Minecraft jar on the test classpath — that is *not* `neoForge.unitTest`, which boots FML. The `test` task runs from `build/test-run` (the game's logger writes a `logs/` next to the working directory) with `maxHeapSize = 2g`. Anything needing a level wants a game test instead.
- **Game tests are declared as content, not as test sources.** A `GameTestLibrary` (see `api/gametest/`) turns one `ToGameTest` declaration into all three things the game holds a test as: the test function goes into `BuiltInRegistries.TEST_FUNCTION` when the library is built, and the `test_instance` entry plus the structure `.nbt` are written on a **data generation run** by `GameTestStructureDataProvider`. A newly declared test therefore does nothing until `runData` has been run and the output committed. A mod names its library on `ToContentMod.gameTests` and on `ToContentDataMod.gameTests`. Only Neoforge has a run for them (`register("test") { type = "gameTestServer" }` in `neoforge/build.gradle.kts`); Loom has no equivalent registered, so `runTest` is Neoforge-only. `ToGameTestHelper` holds the player-facing place/break/drop helpers, and `PlaceBreakDropGameTest` is a ready-made test for multi-position blocks.
- **CI runs builds, data gen diffs, and game tests.** `.gitea/workflows/build.yaml` runs `build` (which includes `test`, `checkstyleMain`, `detekt` and `checkSourceLayout`), then `runData`, then `runTest`, then asserts `git diff --exit-code` and that no `enforcer_report.txt` exists. There is no typecheck beyond Gradle's Kotlin compile.
- **Common code is consumed via capability artifacts, not project references.** `to_sky_and_stars` depends on `:to_base:common` through a declared capability (`net.jidb.to.base:to_base`). You cannot simply `compileOnly(project(":to_base:common"))`.
- **Fabric access wideners** are auto-detected if `[modId].accesswidener` exists under `common/src/main/resources/`. Mixin refmaps use `${modId}.refmap.json`.
- **Neoforge AccessTransformers** are auto-detected from `META-INF/accesstransformer.cfg` if present.
- **Wiki content** lives in `common/src/main/templates/wiki/<modId>/articles/`. Each article is a directory with `index.json`, `en_us/index.md`, optional `factsheet.json` and `changelog.json`. See `.claude/rules/wiki.md` for the complete writing convention guide.

## Architecture Notes

### to_base (library mod)
Provides:
- Multi-platform event system (Fabric service providers + Neoforge Forge events)
- Cross-loader registry registration system ("Libraries")
- Data-driven wiki engine using Markdown/JSON hybrid templates (consumed by the `research_desk` block in-game and the online wiki at `to.jidb.net`)
- Data provider utilities for copying/deleting data and resource assets
- Kotlin helper functions

### to_sky_and_stars (content mod)
Depends on `to_base:common` as a library. Adds uranium ore generation, nuclear items/mechanics, power cables, power banks, machine enclosures, and atomic bombs.

## Adding a New Namespace

1. Create `<name>/properties.toml` with `group`, `version`, `modId`, `modName`, optional `description`
2. Mirror the `common`/`fabric`/`neoforge` directory layout under it
3. Add `include(":...<name>:...")` lines to `settings.gradle.kts`
4. Each loader build.gradle.kts uses plugins `multiloader-loader` + the loader-specific plugin (`loom` or `moddev`)
